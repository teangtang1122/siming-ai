# 司命 3.3.8 已保存章节修订与重新建档对账修复文档

> 目标版本：`3.3.8`（合并补丁）  
> 实施 PR：`#69`，版本对齐补丁随正式发布合并  
> 原则：AI 只生成可审阅候选；正式正文只能由作者确认保存；重新建档更新当前投影，不复制第二份正式数据。

## 1. 问题与触发条件

### 1.1 已保存章节无法由 Agent 生成修订候选

旧流程把 `chapter_writer` 和 `save_external_chapter_draft` 都限定为“未关联正式章节的大纲”。当章级大纲已有正式章节时，工具只能拒绝，且系统没有另一条可写入、可审阅、可恢复的章节正文修订通道。

触发条件：

1. 大纲节点已经关联 `chapters.id`；
2. 作者要求 AI 重写或修订该章；
3. Agent 调用原有章节写作工具；
4. 工具因“已有正式章节”拒绝，前端也没有修订候选接收流程。

### 1.2 手动保存可能覆盖稍后保存的新版本

网页或手机打开章节 v1 后，如果另一端先保存成 v2，旧编辑器仍可提交 PUT。旧接口没有校验“编辑器加载时的版本”，因此后提交的旧页面可能覆盖 v2。

### 1.3 已有大纲在建档后出现重复章节节点

旧建档在处理 `outline_create` 时，会优先按模型返回标题精确查找。立项大纲标题与模型标题只要存在冒号、空格或轻微格式差异，就可能新建一个 catalog 节点，并把章节链接改到新节点。结果是：

- 作者原定章节节点仍在；
- 建档又生成一个内容相近的章节节点；
- 后续场景挂到新节点下；
- 再次建档继续围绕错误节点追加数据。

### 1.4 修改已建档章节后再次建档会追加派生记录

候选记录和应用日志本应是追加式审计历史，但大纲场景、角色/设定时间线、章节关联等用户视图是“当前章节版本的投影”。旧实现混淆了两者，重新建档时容易追加新行，而没有更新或清理上一个版本已经失效的派生数据。

## 2. 修复后的权威行为

| 场景 | 3.3.8 行为 |
|---|---|
| AI 写未保存的新章 | 仍生成 `new` 草稿，作者确认后 POST 新章节 |
| AI 修订已有章节 | 复用现有写作工具，显式提交 `target_chapter_id`，生成独立 `revision` 候选 |
| 作者查看修订 | 正式正文与候选并排对比；候选不会自动进入编辑器 |
| 作者采用修订 | 先显式“应用到编辑器”，再 PUT 原 `chapter_id`；生成 `ai_revision` 快照 |
| 候选生成后正文已变化 | 返回/显示版本冲突，保留正式正文和候选，禁止静默覆盖 |
| 网页或 Android 手动编辑 | PUT 携带 `expected_version`；版本过期返回 HTTP 409，保留本地编辑 |
| 首次建档已有立项大纲 | 优先更新 `chapter.outline_node_id` 指向的节点；保留标题和 `planned_summary`，只更新实际摘要 |
| 修复旧版重复节点 | 重新建档时，如当前链接是 catalog 误建节点且能唯一匹配作者原定节点，迁移其子场景/角色关联、恢复原链接并删除误建容器 |
| 修改章节后重新建档 | 用上一轮候选的目标 ID 对账；更新原记录，删除当前版本已移除的 catalog 派生行 |
| 全局角色/世界观实体不再出场 | 只移除该章关联和派生时间线，不删除全局实体，避免破坏其他章节资料 |
| 重建较早章节 | 不允许较早章节的状态覆盖排序更后的角色/世界观当前状态 |

## 3. 数据模型与接口

`chapter_drafts` 增加：

- `draft_kind`: `new` 或 `revision`；
- `target_chapter_id`: 修订候选绑定的正式章节外键；
- `base_chapter_version`: 开始生成候选时的正式版本。

章节 PUT 增加：

- `draft_id`: 作者正在接受的修订候选；
- `expected_version`: 编辑器加载或候选生成时的章节版本；
- `trigger_type=ai_revision`: 由服务端对修订候选强制写入，不能伪装成普通新章。

迁移版本为 `300a27_chapter_revision_drafts`。升级保留已有草稿，默认把旧草稿标记为 `new`，并为 `target_chapter_id` 建立 `ON DELETE SET NULL` 外键。

## 4. Agent 工具复用

没有新造一套正文覆写工具。3.3.8 扩展现有工具：

- `chapter_writer`：增加可选 `target_chapter_id`；
- `prepare_external_writing_context`：返回目标章节和基准版本；
- `save_external_chapter_draft`：修订时必须回传匹配的 `target_chapter_id` 与 `base_chapter_version`。

服务端执行以下校验：

1. `target_chapter_id` 必须属于当前作品；
2. 它必须与所选章级大纲当前关联的正式章节一致；
3. 外部 Agent 必须沿用准备上下文时返回的基准版本；
4. 生成完成时再次核对章节与大纲绑定；
5. 只持久化 pending 候选，不改正式正文；
6. 作者 PUT 时再次核对目标 ID、候选状态和章节版本。

## 5. 前端与 Android

网页正文页：

- 新章草稿继续独占未保存编辑器；
- 修订候选不会替换正式正文；
- 提供“对比候选”“应用到编辑器”“撤销应用”；
- 当前有未保存手工修改时，替换前二次确认；
- 版本冲突时隐藏应用动作，并保留候选供人工对比；
- 保存成功后更新原章节并显示 `AI 修订` 版本快照。

Android：

- 可在候选和当前正式正文之间切换只读对比；
- 修订候选仅在连接 PC Gateway 时保存；
- 版本冲突时禁用保存；
- 普通手机手动编辑也携带 `expected_version`；
- 离线模式不伪造已有章节修订，避免绕过 PC 权威版本检查。

## 6. 重新建档对账规则

`CatalogingCandidate` 和 `CatalogingApplyLog` 继续追加保存，作为审计历史。用户可见的派生视图按最新一次成功运行对账：

| 派生数据 | 对账方式 |
|---|---|
| 章节摘要 | 更新该章唯一摘要 |
| 章级大纲 | 优先使用章节已链接节点；保留作者规划文本，更新实际摘要 |
| 旧版误建章节点 | 唯一、安全匹配时恢复作者节点并删除 catalog 重复容器 |
| 场景/节级节点 | 以稳定 `scene_number` 或归一化身份更新；移除本版已不存在的 catalog 场景 |
| 场景角色关联 | 对 catalog 场景做精确集合替换；作者规划章节的关联保持增量且不被清空 |
| 角色/设定实体 | 按目标 ID、规范名/别名、归一化标题复用全局实体，不因单章删除而删实体 |
| 角色/设定时间线 | 复用上一轮目标行并更新；清理该章上版已移除的事件 |
| 章节角色/设定关联 | 与本轮完整投影一致，去重并移除失效关联 |
| 建档事实 | 旧运行的 active fact 标记为 `superseded`，本轮事实成为当前版本 |

如果本轮存在 pending、applying 或 apply_failed 候选，系统不执行破坏性清理，防止半成功运行误删上一版数据。

## 7. 验证范围

必须通过：

- 新章草稿仍只能 POST，修订草稿只能 PUT；
- 修订目标不匹配时不写正文；
- v1 候选面对 v2 正文返回 409，两个文本均保留；
- 作者采用候选后原章节 ID 不变，版本加一并产生 `ai_revision` 快照；
- 旧版重复章节点能恢复到唯一作者规划节点；
- 标题标点变化不会再创建第二个章节点；
- 重建档更新场景/时间线，移除上版失效数据；
- 全局角色和世界观实体仍保留；
- 旧章节重建档不回退后续章节产生的当前状态；
- Web 修订对比、应用、撤销、冲突阻断和手动版本保护；
- Android 请求模型和 PC 写入契约；
- `300a26 -> 300a27` 数据库迁移回放；
- OpenAPI 生成文件、前端生产构建及后端回归测试。

## 8. 发布与回滚

发布顺序：

1. 完成三端版本号 `3.3.8` 和迁移回放；
2. 提交临时分支并推送；
3. 创建 PR，等待检查通过后合并到 `main`；
4. 只在合并提交上创建 `v3.3.8`；
5. 发布 GitHub Release 并核对构建资产；
6. 确认远端临时分支已删除，关闭本地临时分支工作区。

数据库升级前会按现有启动流程创建备份。若出现回归，不改写 `v3.3.8` 标签；停止继续分发，从上一稳定标签建立前向修复版本。AI 修订候选和建档候选均保留审计记录，不通过删除历史伪造回滚。
