# 司命路线图

本文以当前 3.5.x 代码线为基线，最近核对版本为 3.5.4（2026-11-06）。已发布变化以对应版本的 Release Notes 为准；这里记录当前能力、尚需推进的方向和验收边界，不重复维护历史版本清单。

## 当前基线

司命已经形成 Windows 桌面、Android 与用户自有 Gateway 三种运行形态。当前核心闭环包括：

- 从一句创意进入对话式立项，审阅结构化资料后建立正式作品。
- 导入既有小说并逐章建档，累计角色、世界观、关系、时间线和叙事治理资料。
- 通过受治理上下文生成未保存章节草稿，由作者决定保存、建档和继续时机。
- 使用 API、本地模型或本机 Agent CLI，并按任务独立选择模型；PC 与 Android 支持按 API、模型保存高级请求参数，手机支持多组 API。
- Android 本机编辑、章节历史与恢复、角色配置及独立 API Agent；手机 API 和本机资料不因保存 Gateway 地址而切换执行位置，Gateway 用于可选同步或作者显式选择的 PC 模型。
- 手机通用会话、工具日志和章节草稿可跨重启恢复；这不等于进入 PC 数据库级 AgentRun 审计。
- 自 3.4.0 起提供调用与上下文查看器，可查看已采集的请求、响应、工具结果及来源，并导出本地脱敏诊断 ZIP；缺失、截断和外部 CLI/MCP 不可见部分明确标注。
- Windows 安装包、签名 Android APK、双架构 Gateway 镜像和自动化发布门禁。

能力存在不等于所有端点、设备和正式资产已完成同等范围实测。当前跨端契约登记 29 项能力：14 项已对齐、15 项部分对齐、0 项待实现；具体状态以机器契约及其生成文档为准。3.5.4 的测试范围和未验证边界见[提交前验证](qa/2026-11-05-release-3.5.4.md)。

## 管理原则

1. 作者控制和数据安全优先于自动化程度。
2. 建档、写作、保存、恢复等核心闭环优先于新增外围功能。
3. PC、Android、Gateway、API、CLI 与 MCP 共用业务契约，不建立入口专属的简化路径。
4. 长任务必须可诊断、可取消、可从持久检查点恢复。
5. 当前代码、生成契约、文档和发布资产必须保持同一版本事实。
6. 已有实现、自动化回归、真实模型验证和正式安装包验收分别记录，不相互替代。

## P0：核心闭环可靠性

目标：任何受支持的模型入口都不会覆盖作者数据、重复执行写入或把失败伪装成完成。

- [ ] 持续扩充“生成草稿 → 作者保存 → 可选建档 → 允许下一章”的跨入口端到端测试。
- [ ] 扩充任务明确选择、任务默认、全局默认及手机多 API 配置的优先级回归，覆盖配置变更、模型不可用和凭据隔离。
- [ ] 在已有建档候选校验和工具参数有界修正基础上，增加缺项、撤回、重复提交、非法引用及失败恢复样例。
- [ ] 对断流、重复请求、取消和应用重启执行故障注入，验证 Operation、AgentRun、手机任务与草稿状态一致；请求已送达或状态不明时不得盲目重放。
- [ ] 扩充历史整理输出超限、结构/引用修正及模型容量边界回归，验证失败保留原文和有效检查点，不继续执行后续业务工具。
- [ ] 持续演练旧数据库升级、未知结构只读恢复、WAL 在线备份及内容镜像 outbox 重放。

验收标准：核心写入具有确定性的幂等边界；失败后保留已完成结果，并向作者给出真实的恢复入口。

## P1：跨端能力收敛

目标：Android 在线、离线与独立 Agent 的差异均有明确产品语义，不以隐藏降级冒充 PC 完整能力。

- [ ] 按 `contracts/mobile-pc-parity.json` 逐项审查 15 项 `partial` 的实际缺口，区分待补业务能力、审计差异和合理平台差异；同步测试和生成文档，不仅为降低数量而修改状态。
- [ ] 在已有手机通用对话与工具日志持久化基础上，明确独立 Agent 与 PC AgentRun 的审计关联和可迁移范围，不伪造 PC 执行记录。
- [ ] 评估世界观关系专用领域命令、手机关系编辑及独立写作消费关系边的安全实现顺序；角色专用配置已可本机编辑，角色扮演模型运行仍是独立缺口。
- [ ] 保持手机领域操作本机执行、可选修订同步与显式远程模型选择的边界，不恢复“在线即由 PC 代办”的旧路径。
- [ ] 为同步冲突、tombstone、撤销设备、手机建档回执和跨版本升级建立稳定的多设备回归场景。
- [ ] 补齐 Android 正式签名安装包的独立创作、诊断查看/导出及移动设备性能实机验收，记录设备、模型、版本和未覆盖范围。

验收标准：能力契约中的每个差异都有原因、用户提示、幂等策略和回归证据；已支持的章节历史与恢复不再列作待实现。

## P1：架构与可维护性

目标：在不改变业务语义的前提下减少超大模块和兼容层，让权威路径更容易验证。

- [ ] 拆分 `context_orchestrator.py`、统一助手流、建档编排和本机 CLI 适配器等超大模块。
- [ ] 将 `gateway` 纳入 `backend/app/modules/manifest.py` 所有权清单，明确其与 `story`、`operations` 的依赖方向并补充相应门禁。
- [ ] 继续将路由中的编排下沉到 application service，并保持路由不直接访问 ORM 或提交事务。
- [ ] 删除已经没有数据迁移职责的 legacy facade、旧命名和重复测试；兼容读取与日常业务路径保持隔离。
- [ ] 逐步降低前端大页面、页面级 API 直连和 `useEffect` 基线。

验收标准：架构检查维持零错误，存量 warning 数量下降，相关模块的公开契约不发生无意漂移。

## P2：作者可见性与诊断

目标：在已有 AI 参考资料和调用查看器基础上，让作者更容易理解 AI 读取了什么、为什么停止以及下一步能做什么。

- [ ] 改进 ContextManifest 摘要、来源覆盖和预算取舍的呈现，明确资料估算、实际 API 请求与提供商实报用量的区别。
- [ ] 对模型路由、CLI/MCP preflight、建档补全和同步冲突逐项核对现有诊断覆盖，补齐实际缺失的结构化原因、关联证据与导出内容，不另建重复采集路径。
- [ ] 完善项目级记忆管理，包括来源、适用范围、停用和删除。
- [ ] 统一桌面与 Android 的运行阶段、错误原因、重试语义和作者确认文案。
- [ ] 继续补齐窄屏、键盘操作、读屏标签以及 loading/error/empty 状态。

诊断 ZIP 与基础查看器已存在。自动 token 归因图、费用计算、OTLP 自动上传和一键重放不是当前已交付能力，也不在本路线图中承诺发布日期。

## P2：发布与供应链

目标：所有正式资产可复现、可验证，并与同一 tag 精确对应。

- [ ] 在已有 `build-toolchain.json` 基础上，收敛 Docker/Gateway 构建中独立写死的 Node.js/npm 版本，补充真源与镜像工具链的一致性检查。
- [ ] 取得可信 Windows Authenticode 证书后恢复签名与时间戳强制校验。
- [ ] 保持 Windows、Android、Gateway、前后端版本和 Release Notes 同步，并在发布时核对路线图及当前架构说明。
- [ ] 定期升级锁定依赖并执行安装包、APK、amd64/arm64 镜像的完整冒烟验证；区分构建成功与正式下载资产的安装、升级及签名验证。
- [ ] 随网络监听、凭据存储和更新策略变化同步修订桌面与 Gateway 威胁模型。

## 近期推进顺序

### 3.5.x 稳定线

优先处理核心闭环缺陷、发布阻断、文档/版本漂移和低风险测试补强。保留 3.5.4 已记录的真实模型测试边界，优先补齐 Android 正式安装包和跨端恢复场景的验收证据。

### 下一次次版本迭代

优先从“跨端剩余缺口与实机验收”“超大模块拆分”“已有上下文诊断的可用性与覆盖补强”中选择不超过三个可独立验收的主题。按分支策略先核对并同步发布基线，再进入 `develop` 集成验证；版本范围和发布日期不在路线图中提前承诺。
