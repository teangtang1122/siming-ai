## 问题与优化

### HA-001：新书欢迎按钮没有可见效果（P2）

复现：空作品库进入 AI 助手，点击“开始新书立项”。欢迎按钮仍然跳转已改为重定向的旧地址，最终回到同一页。

修复：按钮直接将可编辑的立项引导放入输入框并聚焦，已有输入保留，不自动发送或创建作品。仍使用当前统一的 Agent 创作流程。

### HA-002：OpenCode 已验证模型首次创作仍被容量检查拦截（P1）

复现：保存已有 OpenCode 配置并通过真实连接测试，然后发送第一条立项消息。UI 宣称可以创作，但实际流程因未知容量终止。即使点击获取模型，原发现逻辑仍只返回名称。

修复：同一模型发现入口读取 CLI 的 verbose 结构化元数据，验证模型 ID 与容量字段并保留到配置；合并已配置名称时不再丢失容量。手动验证和首次免费激活均保存这些真实元数据，不为未知模型猜测容量，也不绕过上下文检查。CLI 的其他字段（包括 headers）不进入模型选项。

平台边界：本机 OpenCode 发现只属于 PC/桌面 Gateway；Android 独立线路不运行 PC CLI，继续使用自身 API 模型容量契约。此次未新增手机依赖 PC 的路径，需继续回归共享模型与项目包契约。

模型与激活回归：112 项通过；界面回归：29 项通过。包含 verbose 协议解析、重复模型合并、错误 ID/无效容量拒绝、验证及激活后容量可用性，以及欢迎按钮聚焦和保留已有输入。

### HA-003：立项失败缺少可定位诊断（P2）

复现：实际本机模型执行失败，用户只得到笼统报错，服务日志中没有关联的异常原因。

修复：失败事件及持久对话记录保留同一错误编号；服务端记录异常类型与脱敏详情。原始内部异常不回传用户，不泄露 API Key。对应立项回归 62 项通过。

### HA-004：临时 MCP 没有绑定当前运行实例的数据源（P1）

原因：开发服务的数据库可来自 `.env` 或默认相对路径；这些值不一定出现在子进程环境中。MCP 源码入口在缺少 `DATABASE_URL` 时选择安装版目录，因而找不到当前开发实例的持久回合，所有工具被回合归属检查拒绝。原保护机制正确拒绝了不属于该数据库的回合，但上层只呈现“未调用类别入口”。正文镜像目录与密钥文件也存在同类工作目录漂移风险。

修复：所有受管临时 MCP 共用一个运行环境解析入口，传递当前实例的绝对数据库地址、正文镜像目录和密钥文件路径；拒绝无法跨进程共享的内存数据库。密钥路径沿用加密模块的同一解析函数，不读取或复制密钥内容，不修改用户持久 MCP 配置。授权、类别控制、回合归属和写入数量限制全部保留。

验证：真实 OpenCode 握手通过；修复后的真实立项已完成类别切换和当前会话读取。CLI/MCP/立项组合回归 161 项通过，包含跨工作目录的数据路径一致性及内存数据库拒绝。工具连接格式另核对 [OpenCode 官方 MCP 文档](https://opencode.ai/docs/mcp-servers/)。完整创作与导出仍须继续验证。

### HA-005：结构化参数被字符串化后，模型无法从笼统报错中修正（P1）

复现：创意生成模型把工具契约要求的 `changes` 数组编码成字符串，连续三次失败。持久回合审计记录证明未保存创意，保护边界没有被绕过。

修复：统一工具执行入口在处理业务前使用现有同源 ToolSpec 校验参数，失败时返回确定性的 `native_tool_contract_invalid` 和固定类型提示，不反射输入或异常详情。模型必须重新输出符合契约的数组/对象；不增加字符串自动解码、语义猜测或备用业务路径。立项数组字段说明和 CLI 提示同步明确原生结构要求，重建 Android 同源契约。相关结构化输入与手机契约回归 59 项通过。

### HA-006：大资料已经提交，写入回执却超容量报错（P1）

复现：`creation-concepts-02` 的第一笔合法创意写入将版本 2 推进到 3，但工具回执返回整个 artifact，5361 字节超过 4096 字节的状态回执上限。模型收到失败后以旧版本继续请求，引发第二个冲突。最终重新读取才发现创意实际已经保存。审阅时以数据库正式接口的版本 3 原文为准，未采用回复中被缩短的复述。

修复：阶段写入工具只返回阶段标识、会话 ID、版本及影响摘要，完整资料由同一读取工具取得；不截断已生成资料、不提高固定回执上限掩盖问题。版本冲突回执保留当前版本及可执行的重新读取提示。增加大资料经真实 MCP 执行后“正文完整、成功回执小于上限、版本仅增加一次”的回归。

### HA-007：大纲关联人物刷新后顺序漂移（P2）

回归实测暴露：同一次提交的多个人物关联在 Windows 时钟精度下可得到相同创建时刻，读取时再按随机 UUID 打破平局，作者选择的角色顺序不稳定。这会影响大纲呈现与迁移后的可读性。

修复：在现有关联存储路径中，以同一批次时刻加递增微秒记录作者顺序，不引入另一套排序路径。现有人物关联顺序与去重测试复测通过。

### HA-008：MCP 入口帮助输出编码不一致（P2）

回归实测暴露：Windows 入口在 argparse 提前退出前尚未配置 UTF-8，帮助包含非 ASCII 字符，UTF-8 调用方解码线程失败。修复为入口最先配置标准输入输出编码，让帮助、参数错误和正常 MCP 均使用同一 UTF-8 契约；子进程测试明确按此协议读取。

### HA-009：作者容易误解阶段修订的范围（待改进）

真实审阅发现：阶段级修订会保留已存在的世界观实体。文风说明已经按要求变化，但具体条目仍含旧的证据推断；界面显示待确认不能证明每个实体都修改过。这是修订范围和反馈可见性问题，不能据此放宽实体写入边界。

当前操作：从实际实体目录读取 ID，分别对需要修改的条目发起实体级真实模型修订，复读保存结果。建议：在阶段编辑/调整入口说明它不改动既有实体；成功回执展示实际更新字段与保留实体数，引导作者进入具体实体修改。此项尚未计为代码修复完成。

### HA-010：生成保存后实体读取仍是旧版本（P1）

真实复现：阶段版本已由 6 推进到 8，按实体 ID 读取“证据校准方法与时间验证体系”却仍返回版本 6 原文。列表查询会从阶段资料重新构建实体投影，掩盖问题；直接实体读取、下一轮上下文检索可能看到旧数据。

原因与修复：阶段保存使用乐观并发 CAS；成功后刷新父会话，SQLAlchemy 的 refresh-expire 级联丢弃尚未 flush 的实体/历史更新。现于 CAS 成功后、刷新前，在同一事务 flush，版本冲突仍整笔回滚，不增加第二条保存路径。回归先复现旧目标未更新，再验证直接实体读取与阶段版本一致，不依赖列表查询的重建。

### HA-011：缺少目标集合的模型回复被旧资料补成“成功”（P1）

真实现象：档案修复条目的运行记录与输出预览显示模型已经生成新内容，但最终阶段条目未变化。进一步回归证实，当模型套错层级或未返回目标集合时，原归一化先合并 baseline，后续存在性检查读到了旧对象，可能误记生成成功。

修复：先在模型原始结构中验证目标集合与对象，既有实体修订必须恰好返回一个目标；缺少或多目标时让同一模型按契约修复，仍不合规则失败且不推进资料版本。不以旧资料填补生成结果，不用关键词猜测目标。PC 同源生成提示与 Android 导出契约一并明确对象集合结构。

手机独立路径检查：旧实现先生成全阶段，再用原实体下标取生成数组的同一位置；所选第二个实体而模型只返回一个对象时可能无修改仍成功。同步改为按真实已选实体构造范围、校验归属并要求单个结果，只合并所选目标。手机通过自身 Direct API 生成和本地数据写入，不依赖 PC 界面。相关 Android 独立网络协议回归已通过，含在格式错误时保留原始资料的验证。

### HA-012：人物关系字段未完整遵守落库契约（待加强校验）

真实模型返回 15 个人物、19 条关系。关系用 `source/target/type`，正式建档需要 `character_a/character_b/relationship_type`；原入库逻辑对缺少关系类型有通用默认值，存在丢失“母女/合作者”等关系语义的风险。

本书处理：作者审阅后，通过逐实体正式 PATCH 把模型已明确给出的结构字段对齐为正式字段，保持端点、关系文本和关系类别不变，并核验 19 条关系全部引用现有人物。另校订少量年龄/退休表述与英文残留；这些操作有独立 `author_copy_edit` 记录，不算模型生成正文。建议后续加强关系契约提示与写入校验，防止缺字段静默降级。本项尚未计为通用代码修复完成。

地点资料也出现同类风险：模型把用途、环境、权限分别放在自定义字段，未填正式的 `content`；世界观维度使用中文自由值。作者逐条选择真实实体及六维枚举，并把已生成原文按标签排入 `content`，删除重复的自定义字段，未另造地点正文。后续应在正式落库前拒绝不完整字段，不能把“待补充”当作完整资料。

### HA-013：阶段 HTTP 请求未传递显式上下文引用（P1）

原阶段执行器和 MCP 契约已支持 `context_entity_ids/context_artifacts`，但正式 HTTP 请求模型没有这两个字段，调用者无法将已选择的真实实体交给模型。实测卷纲再次沿用旧创意的验证方法，未使用已修订的证据条目。

修复：HTTP 请求接受同一限额的显式 ID 与阶段引用并持久传递给现有执行器；实体归属和有效性仍由同一执行边界检查。不按用户文本预选材料、不添加自然语言路由。新增回归验证引用同时进入持久任务和后台执行参数，21 项相关测试通过。后续细纲将明确选择当前真实人物、地点、证据和卷纲作为引用。

### HA-014：正式立项丢失文本形式的文风规则（P1）

真实资料检查：已确认的 `style_rules/forbidden_patterns` 是完整文本；PC 立项转换只接收数组，因而会丢失该文本，禁用规则还可能静默回退到旧创意预设。测试进一步复现作者清空规则后旧默认规则再次出现。

修复：在同一正式立项转换入口保留文本或文本行数组，按字段是否存在读取默认值，明确的空值不再恢复预设。只转换结构，不拆句、不判断语义。Android 现有 `jsonLines` 已按同一方式保留文本、数组与空值，此次无需增加手机分支。落库回归先复现 3 项失败，再验证修复后 78 项相关测试通过；完整小说正式立项后的字段还须实读核对。

### HA-015：准备阶段失败未持久化，任务永久运行中（P1）

前 3 章细纲任务创建约 248 秒时，Operation 仍为 `running`，但 `health_status=disconnected`，心跳停留在创建时刻，尚无输出片段。进一步核查发现测试请求中有一条由测试作者抄错的时间线实体 UUID；校验正确拒绝了不存在的实体，实际没有启动模型。本次不是一次成功的模型生成，也不是模型超时。

根因与修复：执行器只在生成阶段异常时落库失败，准备阶段异常被返回为工具错误后直接退出，持久任务仍停留在运行中。现对已经创建的任务使用同一 `fail_run` 路径持久化失败、结束时刻、诊断及 Operation；不忽略错误实体、不更改目标。两项回归先复现长期运行状态，再核验拒绝发生于模型调用之前、资料版本不变且任务终止。原测试任务通过正式暂停/取消接口结束，重新读取目录选择真实 ID 后另行重试。

### HA-016：修改实体或上下文后仍重放旧任务（P1）

将 HA-015 中的错误引用改为目录返回的正确 UUID 后，新请求仍返回已取消任务。原自动幂等键只包含阶段、操作、指令、模型与资料快照，没有包含目标实体和显式上下文；因此修正请求但未改动资料版本时被误认为同一请求。

修复：同一幂等键计算补入目标实体 ID/类型/数量、上下文实体/阶段，以及生成与确认选项。只比较结构参数，不理解或改写用户语义。相同结构请求仍复用同一标识，不同选择不再碰撞。真实测试的新作者操作使用接口支持的独立 `Idempotency-Key` 并保存到请求证据，确认实际启动模型后才继续等待。

### HA-017：本机 CLI 类别切换后继续输出误导性失败，反复重选类别（P1）

真实只读运行 `7dd54c75-328f-4bd5-bded-95fcdf2ff798` 连续多步调用类别控制器；某一步在切换后又尝试 `search_outline`，被“当前模型步骤已结束”边界正确拒绝，却向界面输出“工具不可用”。运行约 550 秒后由作者通过正式取消接口结束，没有业务写入。底层只读握手探针能连接，同一真实回合也已经调用控制器，不能把此问题简单归因于模型没有 MCP 能力。

修复：进程监控读取本轮经过校验的类别状态文件，一旦模型已提交新类别、父进程尚未激活下一步，立即结束当前 CLI；继续由原助手循环激活类别和启动下一模型步骤。没有按用户文本预选工具，没有放宽权限或运行令牌。回执分别说明类别切换、章节草稿和大纲草稿，不再把所有终止事件都称为“章节生成”。共享提示词明确首次选择与后续使用的区别；Android 提示词资产通过原导出脚本同步。启动提示改为“正在启动”，不再在握手前宣称已连接。

### HA-043：手机证据引用会静默退化为空选择，PC保留未声明别名（P1）

第十一章首次真实失败中，模型把普通实体ID错当成 `search_task_context` 的证据ID，PC正确整体拒绝。由此复查同一手机工具时发现：契约允许 `item_id`、`chunk_id` 或 `source_type + source_id (+ source_hash)`，Android却只读取 `item_id/id` 并用 `mapNotNull` 丢弃其余对象。非空的无效数组可能因此变成合法空选择并取得生成令牌；PC虽然不丢项，却仍接受契约没有声明的旧 `id` 别名，并在组合引用可能对应多项时取第一项。这是代码审计发现的跨端风险，未声称已在手机实机小说写作中触发。

### HA-047：失败准备回执泄漏已回滚的“幽灵清单”ID（P1）

### HA-048：模型可跳过已选上下文后续页并提前生成（P1）

第十一章实际成功依赖模型自觉按游标读完5页；原服务在 `submit_context_evidence` 返回第一页时就同时返回选择令牌，保存入口只校验令牌。恶意、出错或急于完成的模型可以忽略 `has_more=true`，直接用第一页和令牌生成、保存，服务端无法证明它见过完整证据。页面虽无截断，业务门禁仍不完整。

## 后半程发现并完成的优化

### HA-049：失活世界资料仍可能进入当前创作投影（P1）

世界资料的审计读取原本能够区分 `active` 与 `superseded`，但若当前查询、上下文固定项或搜索路径遗漏状态条件，已被作者取代的旧卡仍可能作为“当前设定”交给模型。真实作品中先识别 4 个近义重复条目，清理后当前条目从 51 降为 47，审计总数仍为 51；作品继续创作后最终保留 85 个当前条目和 26 个失活条目。

修复把当前世界资料的状态条件下沉到权威查询、上下文构建、检索与章节建档目标解析；需要历史的管理/导出接口显式选择审计视图。证据 `worldbuilding-dedup-summary.json`、`worldbuilding-status-audit-r76.json` 和 `worldbuilding-superseded-search-proof-r76.json` 表明历史仍在，但搜索结果没有把失活实体作为当前世界资料返回。

### HA-050：重复启动建档在不同入口间缺少统一幂等语义（P1）

章节页点击、通用 HTTP、工作区工具和外部 MCP 曾各自判断是否创建任务，竞争时可能生成重复任务或对同一章节版本给出不同结果。修复后所有入口调用同一个建档 launcher，以作品、章节和正文版本锁定当前任务，并统一恢复、重试和终态回执。

真实复核连续点击章节入口两次，再调用通用 HTTP 与外部 MCP，四次均复用任务 `fc09c160-bac0-49e3-a9cf-a256939df83c`；建档任务数和运行数均保持 13，没有额外写入。证据见 `live-cataloging-worldbuilding-verification-summary.json` 及四份 `live-idempotency-*.json`。

### HA-051：数据库已失活的世界资料仍残留在本机 Agent 镜像（P1）

状态更新后，内容同步原来可能只写新版本而不移除旧的当前镜像文件。即使 API 返回正确，CLI 仍可能从本机内容目录读到旧设定。修复让同步目标以当前 `active` ID 集合为准，删除不再属于当前集合的镜像文件；RAG 重建同样只索引当前世界资料，历史继续保存在数据库和完整项目包中。

第 36 至 38 章每次建档后都比较数据库当前集合与镜像文件集合；最终源作品两边均为 85，26 个失活 ID 没有镜像命中。回导作品的索引统计也只有 85 个 `worldbuilding` 当前块，而项目包仍完整恢复 111 条世界资料。

### HA-052：REST、工作区工具与 CLI 的候选应用路径不一致（P1）

第 40 章实跑中，模型已经生成完整候选，但受管 CLI 子进程没有取得当前任务的自动应用授权；REST 恢复入口又走了另一段应用逻辑，造成“候选存在、任务未完成”。修复新增唯一的 `apply_pending_cataloging_run` 服务，REST 与工作区工具共同调用；CLI 临时 MCP 明确继承受管任务绑定，应用权限仍由工具执行层验证。

第 41 章成为修复后的实跑验收：1 条摘要、1 条大纲更新、4 条场景创建、4 条人物状态更新、2 条人物更新、5 条世界资料更新和 1 条章节关联共 18 条候选全部自动应用，任务没有人工应用阶段。证据见 `chapter-41-post-catalog-audit.json`。

### HA-053：场景候选缺号或覆盖不完整时仍可进入应用阶段（P1）

真实建档曾产生没有 `scene_number` 的场景卡，重试候选还可能只补局部结果，使场景顺序、人物、关系或世界资料覆盖被误判为完整。修复在候选存储和手工审查入口统一补齐/复用连续场景号，并以结构化 `coverage_manifest` 校验场景数、人物、关系、世界资料和治理检查；覆盖不完整时不能完成应用，纠正重试必须显式替换完整清单。

第 36、37、38 章分别得到连续的 1–4、1–3、1–3 场景序号，应用后检查同时验证摘要边界、关系复用、被拒绝卡片不入镜像和正文哈希。证据为三份 `chapter-3[6-8]-post-apply-verification.json`。

### HA-054：短草稿失败缺少可执行的补写目标（P2）

原写章工具只告诉模型“低于最小字数”，模型容易连续小幅补写后再次失败，且用户难以判断差多少。修复把正文长度校验集中到同一服务：回执同时给出实际汉字数、硬下限、缺少数量、建议目标和建议再增加数量；建议目标在硬下限上预留 10% 缓冲。失败发生在草稿落库和用量确认前，不会把不合格内容伪装成待审草稿。

第 41 章三次逐步接近但仍不足的输出全部被正确拒绝，明确提高目标后一次得到 4,968 个汉字。证据见 `chapter-41-rejected-drafts-audit.json` 与 `chapter-41-draft-author-audit.json`。

### HA-055：本机 CLI 的临时 MCP 可连接到错误运行实例或丢失受管任务范围（P1）

API 进程知道当前数据库、内容根和建档任务，但它拉起的 Codex/OpenCode 子进程原来没有完整、受控地继承这些绑定。结果可能是 CLI 能连接却读取另一个默认运行目录，或读到当前数据但没有自动应用权限。这正是“API 与本机 CLI 看起来做同一件事，结果却不同”的真实根因之一。

修复由启动器显式构造最小环境：传递当前数据库与内容根，以及当前 `SIMING_MANAGED_*`/`MOSHU_MANAGED_*` 作品、章节、任务和阶段绑定；不继承无关受管变量。第 41 章事实、候选两个独立子进程均通过进程级检查，数据库、内容根、权限包、作品、章节、任务和阶段全部匹配，证据为 `chapter-41-catalog-runtime-binding-proof.json` 和 `chapter-41-catalog-candidates-runtime-binding-proof.json`。

### HA-056：小说正文中的询问句被误判为 CLI 权限请求（P1）

第 41 章事实阶段正常读取章节后，原监视器从模型输出正文中看到“是否允许摘录”，便中止受管进程并要求用户到终端授权。这只是小说对话，不是 MCP 的权限事件。修复后作品建档 worker 不再从任意自然语言输出猜权限意图；它已由用户启动且工具权限在进程范围内预先约束，真实 MCP 拒绝仍按结构化错误处理。

同一建档任务在修复后正式重试完成，没有修改章节正文、没有新建重复任务。失败事件保存在 `chapter-41-catalog-failed-events.json`，恢复和完成状态见 `chapter-41-catalog-retry-after-prose-fix.json` 与最终建档审计。

### HA-057：完整项目包回导丢失大纲建档归属状态（P1）

最终包首次通过官方导入接口创建副本后，41 章正文、摘要、人物、关系和世界资料均一致，但 220 个大纲的语义比较失败：项目包 v1 没有单独导出 `cataloging_status`，204 个由建档产生或完成归属的大纲在新作品中变为 `null`。这会让回导作品后续误判哪些大纲已经建档。

修复没有伪造第二种包格式，也没有修改已经导出的包。v1 导入器利用包内持久证据恢复归属：有章节摘要的章节视为已建档，绑定这些章节的大纲及由源章节产生的后代大纲恢复为 `cataloged`。同一份、同一哈希的原包重新导入后，220 个大纲语义完全一致。首次失败审计、清理回执和修复后审计分别为 `project-package-roundtrip-pre-fix-audit.json`、`project-package-pre-fix-copy-cleanup.json`、`project-package-roundtrip-audit.json`；项目包回归 13 项通过。

### HA-058：幂等回导重放仍提示“已创建作品”（P2）

同一包、标题和幂等键的第二次提交正确返回原作品 ID 且 `replayed=true`，但消息仍写“已创建作品”，容易让用户是否生成了重复副本。修复根据真实 outcome 区分“已创建作品”和“已复用此前导入的作品”。重启正式后端后对最终包再次提交，返回原项目 `e49918ad-ffa7-5724-88e7-1c66cf648757`、`replayed=true` 和新文案；证据为 `project-package-import-idempotent-replay.json`。

## API、本机 CLI 与手机端的业务边界

API 与本机 CLI 可以有不同的传输和交互形式，例如 HTTP/SSE 与 stdio MCP、进度日志和终端呈现；它们不能在同一业务能力上采用不同的验证、权限、状态转换、持久化和最终结果语义。本次真实测试确实发现两类漂移：临时 MCP 没有绑定 API 当前运行实例，以及候选应用入口没有共用权威服务。HA-052、HA-055 已把这两条路径收敛，HA-050 又让不同入口对同一章节版本复用同一任务。
