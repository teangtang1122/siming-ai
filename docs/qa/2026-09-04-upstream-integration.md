## 最终容量策略

本次按产品决定保留远程未知模型 **256,000 tokens** 的有界兜底，目的是让不知道如何填写容量的用户仍能开始使用。兜底使用按 UTF-8 字节计数的保守上界，并始终标记为 `unverified`，不会显示成供应商确认的模型档案。

同一精确 `provider/model` 存在已启用档案时，档案优先。后端解析顺序为：

1. 作者保存并启用的精确模型档案；
2. 当前请求携带的已知容量；
3. 本机运行时或官方模型目录确认的容量；
4. 当前请求携带的未验证 256K 兜底；
5. 系统默认 256K 兜底。

PC 设置页允许未知模型不填上下文窗口，并明确说明会临时使用 256K；上下文治理页继续提供精确档案编辑入口。Android 同样允许留空，持久化 `configured`、`catalog`、`fallback` 三种来源；只有 `fallback` 会通过加密信封传递 `capacity_assurance=unverified`。切换任务模型后不会错误沿用另一个模型的手填容量；若目标模型有官方档案则自动使用，否则回到 256K 兜底。

## 合并后的权威业务路径

### 章节修改与重新建档

远程的章节回滚能力与本地的建档幂等能力已组合。语义修改或删除中间章节时，当前章及后续章由该段正文产生的摘要、大纲、人物状态、关系、世界资料、时间线、治理记录和 RAG 投影会按来源回滚，并将受影响章节标为需要重新建档；仅文风润色只有在调用方显式声明 `style_only` 时才保留原建档结果。数据库事务提交后才停止被取代的 worker，避免事务失败却先杀掉有效任务。

章节页、通用 HTTP、工作区工具和 MCP/本机 CLI 都进入同一个 launcher。launcher 用作品、章节和当前正文版本做幂等判断，并以 SQLite 跨进程写锁串行化“检查后创建”。同一版本已经完成或正在执行时返回原任务；正文版本改变或旧任务已失败、取消、跳过、被回滚时才创建新任务。

### 工具契约与手机分页

最终执行器先用同源 JSON Schema 检查协议结构，再用 Pydantic 完成类型验证和规范化；handler 只接收验证后的对象。失败回执包含字段路径、规则和可重试标志，不回显原始参数或密钥。远程取消固定 12 次工具调用上限的改动已保留，同时继续依靠类别切换、授权交集、事务、写入门禁、超时和取消限制运行。

Android 查询统一使用一个分页实现，保留总数、稳定游标、`has_more` 与 `next_arguments`，并继续过滤失活世界资料。PC 提示契约、Android 资产和前端 OpenAPI 类型均从最终后端重新生成，没有保留冲突时的手工拼接版本。

### 项目包

远程对包外 checkpoint 引用的过滤/验证修复与本地对旧 v1 大纲建档状态恢复、幂等重放文案的修复同时保留。完整包仍保存失活历史；导入后的当前 RAG 只重建有效投影。

### 集成回归中新发现

无上下文 manifest 的外部章节草稿保存成功后，原路径仍会用空 ID 再查询一次 manifest。该多余查询既浪费一次数据库往返，也让严格的 MCP 事务可见性测试出现查询序列漂移。现已改为只有真实 manifest ID 存在时才加载详情；无 manifest 时直接按正文返回确定性的字符和 token 计数，保存事务语义不变。

远程新增的“直接 CLI 可超过旧六步上限”回归最初连续请求同一个已开放类别，与本地高可用路径的 `categories_already_active` 防空转规则冲突。最终测试改为在两个合法立项类别间实际切换七次并在第八步完成：重复类别仍被幂等跳过，真正的多步工作也不再受旧六步上限限制。

全量回归还发现建档候选 PromptSpec 因多轮高可用补充而膨胀到 7,402 字符，已超过 2.9 版 6,530 字符基线。此次把重复散落的约束收敛为一份 4,711 字符的权威合同，保留精确 ID、防重复、匿名身份、字段所有权、旧背景逐字保护、增量修复和叙事账本要求；当前比基线缩短 27.86%，提示词体积门禁恢复通过。

前端全量回归与后端扫描、Android 构建并发执行时，`GuiAssistantChat` 中一个异步保存失败场景曾超过默认 15 秒限制；该用例在 30 秒诊断阈值下通过，并在高内存扫描结束后以原始 15 秒阈值独立通过。最终在机器资源空闲时用单 worker、原始阈值重跑全部前端测试，该用例耗时 4.192 秒，51 个测试文件和 271 项测试全部通过。因此本轮把该现象记录为测试机资源争用，而不是通过永久放宽超时掩盖。

### 未建档章节草稿可由 AI 连续修改（HA-059）

用户反馈属实：旧路径把任何待保存草稿都当成“必须先保存并建档”的阻塞条件，模型不能读取并替换这份草稿，因此作者对初稿不满意时只能先把不满意的内容写入正式章节。现行路径把“继续修改当前草稿”加入同一权威写作流程，同时继续阻止生成下一章：前端在每次请求前把编辑器全文同步到待保存草稿，请求只传真实 `active_chapter_draft_id`；后端校验该 ID 属于当前作品、仍为唯一待保存草稿且绑定当前章级大纲，然后让模型读取完整草稿并原位替换同一记录。保存、建档和继续下一章仍由作者决定。

为防止数分钟模型运行覆盖作者的新修改，后端按模型实际读取的完整草稿状态生成来源哈希，并在写回时加作品级锁重新核对；草稿已被编辑、保存、丢弃或另一轮修订替换时，迟到结果会被拒绝。PC 编辑器还会在任务结束时比较请求基线与当前编辑器内容，发现并发手改后把作者版本重新同步到 API。API、工作区工具、本机 CLI/MCP 和 Android 均使用 `source_draft_id` 与同一归属、状态和来源版本契约，没有保留入口专用的草稿语义。

真实界面按以下流程复验，使用 `codex_cli:gpt-5.6-terra`，模型状态为 `ready`，上下文窗口 1,050,000 tokens：

1. 在 41 章完整回导副本中新建第 42 个章级大纲，通过工作区助手生成待保存草稿；草稿 ID 为 `0db55776-5331-41a9-82c7-30cae5af0fc1`，正式章节仍为 41。

3. 再次请求 AI 修改，并在运行期间追加“这行人工修改不得被迟到的模型结果覆盖”。任务完成后编辑器和 pending API 都保留 1,618 字符、SHA-256 `a506e98e…` 的作者版本，标记句仍在；SQLite 中该作品只有一条 `chapter_drafts` 记录。

## API 与 CLI 会不会不同

传输和交互可以不同：REST 使用 HTTP/SSE，本机 CLI 使用 stdio MCP，手机可经 Gateway 或独立 Direct API；它们也会显示不同的进度日志。业务结果不能不同：目标 ID 归属、参数验证、权限、章节草稿边界、建档状态机、候选应用、重试、取消和最终持久化语义必须一致。

真实长篇测试确实发现过两种入口漂移：CLI 临时 MCP 曾连接错误数据源或丢失受管任务范围；REST 与 CLI 曾使用不同的候选应用逻辑。当前实现通过最小且显式的数据库/内容根/任务环境绑定，以及唯一的 `apply_pending_cataloging_run` 和建档 launcher 收敛这些路径。手机端继续独立运行，不依赖 PC 界面状态。

## 反复建档与重复词条

旧实现对同一章反复启动建档时，确实可能创建多个任务并产生重复或近义人物、世界资料和场景词条。现行路径在任务入口先阻止重复执行，在候选应用时再按当前实体和稳定场景号做幂等更新，因此相同章节版本的重复点击、HTTP 重试或 CLI 重试会复用同一任务，不会再次应用一套候选。

真实作品第 33、35 章分别从 MCP 重复启动，均返回 `idempotent_reuse=true` 和既有已完成任务。该保护针对“同一正文版本”。正文语义发生变化后，旧投影必须失效并重新建档；新的内容如果与现有资料近义但并非同一结构化目标，仍需要作者在候选复核或重复项管理中决定合并，应用层不会用名称关键词替作者猜测实体身份。

## 旧版错误世界资料对后续创作的影响

状态为 `superseded`、归档或草稿的旧条目不会以“当前设定”进入后续创作。它们仍保存在审计历史、版本、章节关系和 `full` 项目包中，但默认列表、目标解析、上下文固定项、RAG 当前索引和本机镜像只使用 `active` 条目。

有一个必要边界：错误条目如果仍被标为 `active`，它仍会影响创作；作者应把它修正或取代。历史章节正文里原本写过的旧说法仍可能作为历史原文被检索，但不会被包装成当前世界资料卡。
